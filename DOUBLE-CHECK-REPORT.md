### Rotation procedure for the Docker host (ordered — names only, no values)
Untracking stops *future* exposure. It does **not** erase the past — the old values remain in git history (locally and on origin) in every clone until history is rewritten (step 6). Rotation is what neutralises the leaked values. Do the backup in step 0 before pulling the untracking commit. Generate every new value offline with `openssl rand -base64 48` (or equivalent); never reuse a value from the old files and never paste a value into git, chat, or a ticket.

**Step 0 — Prepare (before pulling anything).** On the Docker host, copy `api/.env.blockchain` and `api/.env.blockchain.fixed` outside the repo, then pull, then restore both files to `api/`. Take full backups first: Postgres dump, CouchDB data volume, peer ledger volumes, and a copy of the current env files. Confirm the API and all peers are healthy before starting so there is a known-good baseline to compare against after each step.

**Step 1 — `JWT_SECRET` (first; independent, cheapest).** Lives in `api/.env` (gitignored, not tracked). Set the new value there, restart the API only. Verify: API starts (startup gate requires a strong secret), old tokens are rejected (401), a fresh login works.

**Step 2 — CouchDB password (`COUCHDB_PASSWORD`).** Three places, all must change together: the `COUCHDB_PASSWORD` env of the CouchDB service, `CORE_LEDGER_STATE_COUCHDBCONFIG_PASSWORD` on **every** peer (ECTA, ECX, Banks, NBE, Customs, Shipping), and `COUCHDB_PASSWORD` in `api/.env.blockchain`. Update all three, restart CouchDB first, then restart all peers. Wrong order (either side alone) → every peer fails to reach its state database and chaincode invocations/queries fail. Verify: peer logs show successful CouchDB connection, a chaincode query (e.g. `QueryAllLCs`) returns data, the API's CouchDB reads work.

**Step 3 — Postgres password (`POSTGRES_PASSWORD` / `DATABASE_URL`).** `ALTER USER … WITH PASSWORD` inside Postgres **first**, then update `DATABASE_URL` everywhere the API reads it, then restart the API only (Postgres needs no restart after `ALTER USER`; the `POSTGRES_PASSWORD` compose env only takes effect on first initialisation — update it too for any future re-init). Wrong order: API restarted with the new `DATABASE_URL` before the DB user is altered → API fails its startup gate; DB altered while the API still has the old URL → API loses the database mid-run. Verify: API health OK, migration count correct, login + a DB-backed read/write succeed.

**Step 4 — Redis password (`REDIS_PASSWORD`).** Two places: the Redis service env and the API's `REDIS_PASSWORD`. Update both, restart Redis, then restart the API. Either side alone → Redis auth errors in API logs. Verify: no Redis auth errors, API health OK, a cache-dependent operation works.

**Step 5 — Fabric CA / enrollment credentials and the tracked private keys under `blockchain/organizations/` (LAST; maintenance window; most disruptive).** Exposed: 1048 tracked files, 138 private-key files — per org: `ca/priv_sk` and `tlsca/priv_sk` (CA private keys), peer/orderer `msp/keystore/priv_sk`, and `users/Admin@…` / `User1@…` / `User2@…` `msp/keystore/priv_sk`. A CA private key cannot be "changed" like a password — rotating it invalidates **every certificate it signed**. This requires regenerating crypto material, rebuilding the channel configuration (MSP definitions embed the CA root certs), re-deploying peers/orderer with the new MSPs, and re-enrolling the API wallet identities (`FABRIC_WALLET_PATH=./wallet`) — effectively rebuilding the network and re-joining the channel. Ledger data is tied to the old MSPs, so plan it as a rebuild with the step-0 backups in hand. Partial rotation: replacing only a peer's keystore while the channel config still trusts the old CA → endorsement fails; replacing only the CA cert without re-issuing peer certs → all peers orphaned; rotating only the TLS CA → every TLS handshake breaks; forgetting the API wallet → every Fabric call from the API fails with identity errors. Verify after: peer and orderer logs clean, channel config fetch succeeds, a chaincode query succeeds, and one end-to-end transaction through each org's identity succeeds.

**Step 6 — Purge history (only AFTER all rotations above).** Once every leaked value is dead, rewrite history to remove the two files (and ideally the `blockchain/organizations` private keys) with `git filter-repo` or equivalent, then force-push and have everyone re-clone. Doing this *before* rotation gains nothing — the values would still be live on the host — and a botched rewrite before rotation risks losing the only record of what needs rotating. Verify: fresh clone contains neither file in any commit, `git log --all -- api/.env.blockchain*` is empty, and the host still runs with the restored/rotated on-disk files.

**Final verification checklist (after each step, not just at the end):** API healthy on its port, login works, one representative read and one write succeed per affected store (Postgres, CouchDB, Redis, Fabric), and `docker compose ps` shows all services up with no restart loop. If any step's verification fails, stop, restore from the step-0 backup, and do not proceed to the next secret.
