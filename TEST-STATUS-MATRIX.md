# GoCBC — Status Transition Matrix (TEST-STATUS-MATRIX)

**Scope:** every status transition for every workflow entity, compared across four layers:
`CHAINCODE` (chaincodes/coffee/*.go — on-chain source of truth) · `API` (api/src/utils/statusManager.ts + route-level guards) ·
`POSTGRES` (api/src/migrations/*.sql CHECK constraints / enums / defaults, and the status values routes write) ·
`UI` (ui/src/components/portals/*.tsx status unions, filters, status-gated actions).

**Branch:** fix/auth-chaincode-audit (audit started at HEAD aa0947f; fixes applied on top — see §16).
**Chaincode verification:** STATIC-ONLY — no Fabric peer exists on this machine, so chaincode transitions are verified by reading the validator/function code, never by a live call. Any chaincode change listed here needs a re-package + redeploy of `coffee` chaincode on the Fabric host to take effect.
**API/Postgres verification:** LIVE where a Postgres path exists (local API port 3001, Postgres 16, no Fabric). Chaincode-only transitions are marked STATIC-ONLY.
**Counting rule:** "transitions checked" = table rows below. "Disagreements found" = §16 fix entries + §17 remaining entries. A row can carry more than one disagreement; the counts count entries, not rows.
**Postgres note (handoff audit):** every `no CHECK` in the Postgres column of §§1–15 predates migrations 059 (23 CHECKs, §16 #22) and 060 (extensions + `uq_post_delivery_tracking_shipment_id`, §16 #31). The CHECK state is recorded in §16 #22/#31, not per-row — do not re-derive it from the row cells.

**Legend:** `ALLOW` = the layer permits the transition · `REJECT` = the layer blocks it · `NOT-MODELLED` = the layer has no representation of it (no table entry / no column constraint / no UI value) · `UNGUARDED` = the layer accepts it from any state (no from-state check) · `DEAD` = declared but never assigned by any code in that layer.
